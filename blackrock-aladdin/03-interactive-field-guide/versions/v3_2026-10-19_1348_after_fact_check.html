What Aladdin is

Aladdin is the software BlackRock built to run its own investment business, then sold to other institutions. One system holds what each portfolio owns, every order and trade, the rules each portfolio must obey, the cash it has available, its accounting records and its risk numbers. The product's value is that one booked trade updates every one of those views at once.

The investment process in six roles

A client hands money and a mandate to an asset manager. A portfolio manager decides what to buy or sell and raises an order. A trader executes it with a broker. A day or two later the trade settles: cash and securities change hands at the custodian, the bank that holds the client's assets. Accountants record each purchase as a lot and compute the fund's daily price, the NAV. Compliance and risk teams check every step against the mandate and regulation. Aladdin is the system the investor-side roles share; custodians and fund administrators connect to it through the Aladdin Provider network rather than working inside it.

Who uses it

Asset managers, asset servicers and fund administrators, banks and brokers, corporate treasuries, insurers, pension funds, private-markets managers and investors, and wealth managers. Sold only to institutions, in BlackRock's words "institutional, wholesale, qualified and professional" clients; the retail investors whose portfolios wealth managers run are on the platform without being its customers. BlackRock quotes hundreds of clients across 70 countries.

How it is delivered

Hosted software. Each client gets its own Aladdin environment (a tenant), but every environment runs the same code and sits under one control plane, so BlackRock pushes the same software to all clients. BlackRock staff can be granted access into a client environment as "provider" users. Hosted on Microsoft Azure today, with an AWS option expected in late 2026.

How it is layered

Every caller, whether a BlackRock app, a client script or Copilot, enters through the same gateway and the same domain services. There is no privileged path. The domain split is deliberate: Aladdin began as literally one database, trading was later carved out onto its own store, and BlackRock now says the domain, not the database, is the source of truth for its data. Anatomy of one request

Follow a portfolio manager's order from a Python script to a booked order with a compliance verdict. Watch for three things: two separate permission checks, compliance running inside the order post rather than as its own call, and the HTTP response coming back before the work is done.

Design conventions you can see in every spec

The same dozen patterns repeat across all 54 APIs, which is itself the finding: the platform is governed, not grown. Each card gives the pattern, the evidence in the documents, and why it matters to someone building on or running the platform.

The product family

The core products are entry points onto one set of positions and portfolios, so a client that starts with Aladdin Risk and later adds the full platform does not reload its data. eFront is the exception: a separate private-markets suite with its own book of record that is integrated with Aladdin. BlackRock's strategic frame for all of it is the "whole portfolio", public and private assets in one view. The APIs in this guide belong to the core; Studio is how clients build on it.

Where AI plugs in

Aladdin Copilot is an assistant embedded across the apps. When it needs data or wants to act, it calls Aladdin APIs as "tools", the same governed APIs Studio exposes to clients. That is why API quality and AI readiness are one problem for the platform team.

Federated ownership

The central AI team owns orchestration, guardrails and evaluation. Domain teams onboard by registering existing production APIs as tools or by building custom agents, and every plug-in must come with ground-truth examples. That mirrors the domain split in the API namespace. BlackRock also expects clients to want its orchestrator or plug-ins inside their own copilots, and Aladdin plug-ins inside Microsoft 365 Copilot labelled "powered by Aladdin".

Evaluation-driven development

Synthetic data, subject-matter-expert cases and model-graded pipelines run on every pull request and nightly, with reports per plugin owner. The team compares it to test-driven development. This is recent: in late 2024 BlackRock's head of AI product said there was no universal way to score responses and that getting past proofs of concept was the hard part.

Why it matters for Studio

An agent can only use an API that describes itself well: clear metadata, consistent methods, fine-grained scopes. Studio's head of engineering frames the AI strategy as three-fold: AI in every product, AI as a platform for builders, and AI to help the builder write code. The risk product team says it is refactoring data models so they are "structured for agentic use cases".

Names that leak through the docs

Internal systems, modules and jargon the API descriptions mention by name. They appear in the API text itself, so an interviewer will recognise them.

Questions worth asking them

  1. Of the public APIs, nearly half are alpha. How does an API graduate to stable, and how do you handle clients who built on alpha when it changes?
  2. Compliance and Risk Governance are two limit frameworks with separate rules, exceptions and workflows. Are they converging?
  3. What share of Studio usage is BlackRock's own teams versus clients, and what is the path from internal success to external adoption?
  4. Is the Copilot plugin registry fed from the same catalog as the Studio developer portal, or are they separate?
  5. Where is the line between exposing something as an API, as a Data Cloud dataset, or as an event stream?
  6. The specs still cite legacy permission codes under OAuth scopes. Is the goal to retire those, or to keep two layers?
  7. What changes for Studio when a client is hosted on AWS rather than Azure?
